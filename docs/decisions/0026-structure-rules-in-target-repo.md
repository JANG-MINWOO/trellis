# ADR-0026: 구조 규칙은 대상 저장소의 `.trellis/`에 두고, 엔진은 git 트리를 읽는다

- 상태: 채택
- 날짜: 2026-10-10
- 결정한 사람: 에이전트 제안 (PLAN M3) → 미누 진행 승인, 미누 확인(2026-10-10): 대상 저장소에 `.trellis/`가 생겨도 괜찮다

## 결정
규칙은 대상 저장소의 `.trellis/rules.json`(긴 파일, 파일이 몰린 폴더, 중복 코드, 순환 의존, 경로 경계, 제외, 별칭), 기준선은 `.trellis/baseline.json`(얼려 둔 위반의 지문 목록)에 둔다. 파일이 없으면 기본 규칙으로 보여주기만 하고, 두 파일 모두 사람이 버튼(시작 템플릿, 기준선 얼리기)을 눌러야 생긴다. 엔진은 언어와 무관하게 파일 목록·줄 수·import 그래프로 판단하고, import 추출은 TS/JS(tsconfig paths·별칭 포함), Python, GDScript(`res://`), Java/Kotlin, 셸 `source`를 지원한다. 파일은 git 트리(작업 사본 스냅샷, 턴 시작·끝)에서 읽고 내용 단위로 캐시한다. git이 없는 폴더는 폴더를 직접 읽는다. dependency-cruiser·import-linter·ArchUnit 같은 기존 도구는 따로 읽지 않고, 프로젝트의 검사 명령(ADR-0027)으로 돌린다.

## 이유
규칙이 저장소에 있어야 팀원과 다른 에이전트도 같은 규칙을 보고, 커밋으로 바뀐 이력이 남는다(원본 하나). git 트리로 읽으면 .gitignore가 자동으로 적용되고, 턴 시작과 끝을 정확히 비교할 수 있으며, 같은 내용은 한 번만 읽는다. 기존 도구의 결과 형식을 각각 해석하는 것보다 그 도구를 실행해 실패를 되돌리는 것이 스택 무관 원칙에 맞다.

## 대안
- 규칙을 Trellis 데이터 폴더에만 저장: 혼자만 보이고, 저장소를 옮기면 사라진다.
- 언어별 정식 파서: 정확하지만 스택마다 의존성이 늘어난다. 정규식 추출은 놓치는 import가 있을 수 있지만 오탐은 적다(해석되지 않는 import는 간선이 되지 않는다).

## 결과와 대가
측정: 파일 1천 개 저장소에서 갱신 한 번 약 0.5초(대부분 스냅샷), 7천 개에서 약 0.7초(분석 CPU 약 0.5초, 메인 프로세스). 더 큰 저장소는 M5에서 작업 스레드로 옮긴다. 중복 검사는 의미 있는 줄 12줄 이상이 같을 때만 잡고, 주석·import·괄호 줄은 뺀다.
